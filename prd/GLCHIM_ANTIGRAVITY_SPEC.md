## 1. 서비스 정의

### 1.1 이름과 메시지

- **제품명:** 글침 (GEULCHIM)
- **서비스 한 줄 설명:** 사용자가 문장별로 AI의 개입 범위를 선택하고, 제안을 참고해 원문을 직접 수정하는 선택형 퇴고 에디터
- **핵심 문구:** **“AI는 제안하고, 수정은 내가 결정한다.”**
- **핵심 가치:** 글쓰기 주도권, 원문의 보존, 효율적인 부분 수정

### 1.2 문제 정의

일반적인 채팅형 AI에서도 문장 교정, 부분 수정, 문체 보존은 가능하다. 따라서 글침은 **“AI는 이걸 못 한다”** 라고 주장하지 않는다.

글침이 풀려는 문제는 **여러 문장에 서로 다른 수정 권한을 주고, 수정 전후를 확인하면서, 필요한 부분만 원고에 반영하는 작업 흐름이 번거로울 수 있다**는 점이다. 하나의 전용 에디터에서 이 과정을 빠르게 처리하는 것이 목표다.

### 1.3 제품 차별성 — 반드시 구현으로 보여줄 것

1. **문장별 개입 권한:** 사용자가 각 문장을 `진단만` / `AI 고쳐쓰기` / `고정`으로 구분한다.
2. **프로그램 수준 보호:** 고정된 문장에 대한 AI 적용을 **프롬프트 지시가 아니라 애플리케이션 로직**으로 차단한다.
3. **작성자 직접 편집:** AI 제안은 참고 자료일 뿐이며, 사용자가 각 문장의 본문을 직접 타이핑해 고칠 수 있다.
4. **부분 반영:** AI 제안을 누르면 **해당 문장만** 교체되고, 다른 문장과 고정 문장은 유지된다.
5. **의도치 않은 덮어쓰기 방지:** 사용자가 이미 고친 문장에 예전 AI 제안이 덮어씌워지지 않는다.
6. **분석 결과와 편집이 연결:** 글을 문장별 카드로 쪼개고, 그 자리에서 수정하며, 최종 원고가 즉시 갱신된다.

이 차별성의 실제 효율성은 추후 사용자 테스트에서 측정한다. 검증하지 않은 속도·정확도 우위를 홍보 문구로 사용하지 않는다.

## 2. 핵심 UX — 변경하면 안 되는 사용자 흐름

### 화면 A. 시작 / 글 입력

1. 사용자가 큰 텍스트 입력창에 원고를 붙여넣거나 직접 쓴다.
2. `예시 글 넣기`, `내용 지우기`, `분석하기` 버튼을 제공한다.
3. 글자 수·문장 수(대략)를 확인할 수 있다.
4. `분석하기`를 누르면 기존 원고를 문장 단위로 분리하고 **화면 B로 이동**한다.
5. 문단 구분, 줄바꿈, 원문 내용이 가능한 한 보존되어야 한다.

**중요:** `분석하기` 전부터 카드가 나열되는 방식이 아니라, **원고 입력 → 분석하기 → 문장별 카드**라는 단계가 명확해야 한다.

### 화면 B. 문장별 퇴고 작업실 (핵심 화면)

- 왼쪽 넓은 영역: **문장 카드 목록**. 각 카드에 번호·문장 편집창·3가지 개입 모드·분석/AI 결과·적용 및 복원 버튼을 둔다.
- 오른쪽 보조 영역: **실시간 최종 원고 미리보기**, 전체 문장 수/수정 문장 수/AI 고정 문장 수/글자 수 등 간단한 통계, 복사·TXT 다운로드.
- 상단: `원고 다시 입력`, `수정 전후 비교`, `모든 수정 복원`.
- 문장 카드에서 사용자가 직접 글을 고치면 **오른쪽 최종 원고에 즉시 반영**되어야 한다.
- 카드가 수십 개가 되더라도 편집창이 답답하지 않도록 카드 간 여백과 텍스트 크기를 충분히 확보한다.

### 화면 C. 수정 전후 비교

- **최초 분석 시의 원고**와 **현재 작업 중인 최종 원고**를 나란히 표시한다.
- 변경된 구간을 알아보기 쉽게 표시한다(최소한 문장별 변경 표시; 가능하면 단어/문자 단위 diff).
- 사용자는 비교 화면에서 작업실로 돌아갈 수 있다.

## 3. 가장 중요한 정책: 3가지 모드의 의미를 절대 혼동하지 말 것

화면의 사용자용 버튼 이름은 다음을 권장한다. 기존 데모의 `수정 제안`과 `AI 수정`이 혼동되므로 **서로 다른 결과를 내도록 엄격히 구분**한다.

| 모드 | 화면 이름 | AI가 수행할 작업 | 사용자 행동 | AI 문장 자동 적용 |
|---|---|---|---|---|
| `advice` | **💬 진단만** (기존 ‘수정 제안’) | 문제점·개선 이유·방향을 **설명만** 함. 대체 문장 미생성 | 설명을 보고 **직접 편집** | 불가 |
| `rewrite` | **✨ AI 고쳐쓰기** (기존 ‘AI 수정’) | 원문과 수정 이유를 포함한 **대체 문장** 제안 | 제안을 **적용**하거나 참고해서 **직접 편집** | **사용자가 적용을 눌러야만** 반영 |
| `lock` | **🔒 고정** | 해당 문장에 대해 진단·대체 제안을 생성하지 않음 | 사용자는 **직접 편집 가능** | **항상 불가** |

- `고정`은 **AI에게서 원문을 보호**하는 것이지, 작성자의 타이핑을 막는 `읽기 전용`이 아니다.
- `진단만`에서도 사용자가 직접 수정하면 결과에 반영된다. ‘AI 수정을 사용하지 않으면 못 고친다’는 흐름은 금지한다.
- `AI 고쳐쓰기`에서 결과가 나와도 **자동으로 덮어쓰지 않는다**.
- AI의 제안을 적용한 후에도 사용자가 그 문장을 다시 고칠 수 있다.
- 각 문장 모드는 클릭할 때 바로 눈에 띄게 전환되어야 한다.
- 각 카드에서는 현재 모드에 해당하는 내용만 보여준다(비활성 버튼이 혼란을 주지 않도록).

### 사용자 예시

원문: `전시가 정말 좋았고 작품도 정말 인상적이었다.`

- **진단만:** “강조 표현 ‘정말’이 반복됩니다. 강조할 지점을 골라 보세요.” → 사용자가 편집창에 직접 수정.
- **AI 고쳐쓰기:** `전시 분위기가 좋았고 작품들도 인상적이었다.` + 변경 이유 표시 → 사용자가 **적용**을 누르거나, 원문을 직접 고침.
- **고정:** AI는 해당 문장을 건드리지 않음 → 작성자가 편집창에서 바꾸는 것은 허용.

## 4. 기능 요구사항

### P0 — 첫 실행에서 반드시 동작

#### F01. 원고 입력 · 문장 분리

- 시작 화면에서 빈 글·예시 글 모두 지원.
- `분석하기` 클릭 시 한국어 문장 단위로 카드를 만든다.
- 카드에 **안정적인 식별자(`sentenceId`)**를 부여한다. 단순 배열 인덱스를 AI 제안 ID로 쓰지 않는다.
- 문단 경계를 보존하고 최종 조립 시 자연스러운 공백·줄바꿈을 유지한다.
- `...`, 큰따옴표, 따옴표, 괄호, `3.14`, 숫자, 줄바꿈 등 경계 사례를 가능한 한 처리한다. 완벽한 언어학적 분리라고 주장하지 않는다.
- **사용자가 카드 안에서 문장을 편집하는 순간마다 전체 원고를 자동 재분리하지 말 것.** 타이핑 중 카드·커서·권한 상태가 사라지면 안 된다.
- 사용자가 문장을 합치거나 새 문장을 만든 경우, 재분석/카드 재구성은 **명시적 버튼**과 확인 안내로 처리할 수 있다.

#### F02. 카드 안에서 원문 직접 수정

- 모든 모드에서 textarea/에디터를 통한 **자유로운 직접 편집** 지원.
- 수정 중 커서 점프나 입력창 포커스 손실이 없어야 한다.
- 각 카드의 `원문 복원`은 **그 카드만** 최초 분석 당시 내용으로 되돌린다.
- 오른쪽 최종 원고 미리보기는 사용자의 입력과 동기화한다.
- 키보드 탭 이동, 명확한 포커스 표시 등 기본 접근성을 지킨다.

#### F03. 문장별 모드 변경

- `진단만 / AI 고쳐쓰기 / 고정`을 카드마다 독립 설정.
- `고정`으로 변경하면 보류 중인 AI 적용이 불가능해진다.
- 다른 카드의 모드에는 영향이 없어야 한다.
- 데모 모드에서는 각 모드 결과가 실제로 달라야 한다.

#### F04. 진단만

- 카드의 현재 문장에 대해 **구체적인 검토 이유만** 보여준다.
- 예: 반복 강조어, 지나치게 긴 문장, 어려운 표현 후보, 불필요할 수 있는 부사 등.
- **완성된 대체 문장을 제시하지 않는다.** 이것이 AI 고쳐쓰기와의 핵심 차이.
- 오탐 가능성이 있으므로 “틀린 문장”이 아닌 “검토할 표현”으로 표현한다.
- API가 없다면 가벼운 규칙 기반 진단을 제공하고 `데모 분석` 표기를 붙인다.

#### F05. AI 고쳐쓰기

- 선택한 문장을 모델에 보내 **대체 문장 + 수정 이유**를 얻는다.
- 응답은 원문과 확실히 구분된 제안 패널에 표시한다.
- `이 문장에 적용`과 `다시 제안` 동작을 제공한다.
- `이 문장에 적용`은 **그 카드 하나**를 교체한다. 문서 전체를 AI의 반환값으로 교체하지 않는다.
- AI가 제안을 생성하는 동안 카드 단위 로딩·실패·재시도 상태를 표시한다.
- 데모 모드에서도 실제로 눌러보고 적용할 수 있는 대표 수정안을 제공한다. 단, **실제 AI라고 속이지 않는다.**

#### F06. 오래된 AI 제안 방지 (필수 안전장치)

- 제안을 만들 때 해당 문장의 `sourceText`와 `sourceVersion`을 함께 저장한다.
- 그 후 사용자가 직접 문장을 바꾸었다면 기존 제안은 **stale(오래된 제안)** 상태가 된다.
- 이 상태에서 적용 버튼을 비활성화하고 `원문이 바뀌었습니다. 다시 제안받기` 안내를 표시한다.
- `고정` 상태인 카드에는 제안을 적용할 수 없다.
- API 응답이 늦게 도착해도 이미 변경한 문장을 덮어쓰지 않는다.

#### F07. 최종 원고 실시간 반영

- 카드의 현재 텍스트를 바탕으로 원고를 조립한다.
- 오른쪽 최종본은 **항상 현재 편집 내용과 일치**해야 한다.
- `최종 원고 복사`, `TXT 다운로드`가 실제로 동작해야 한다.
- 한국어 UTF-8로 저장한다.

#### F08. 원문 비교 · 복원 · 자동 임시저장

- 최초 원본과 현재 결과를 비교할 수 있다.
- 카드별 원문 복원 및 전체 복원 제공. 전체 복원에는 확인 대화상자 제공.
- 새로고침했을 때 작업 내용이 사라지지 않도록 브라우저 로컬 임시 저장 지원.
- 사용자가 `새 글 작성`을 선택할 때 기존 작업이 사라질 수 있다는 경고 제공.
- 저장 데이터에는 최소한 원본·문장별 수정본·모드·제안 상태가 포함되어야 한다.

### P1 — P0 구현 후 추가

- 글자 수, 문장 수, 수정된 문장 수, 각 모드별 문장 수 표시.
- AI 수정 목적 선택: `간결하게`, `자연스럽게`, `쉽게`, `반복 줄이기`.
- AI 수정 강도: `최소`, `보통`, `적극`.
- 여러 문장의 모드를 한 번에 변경하는 기능.
- Undo/Redo(실행 취소/다시 실행): 최소한 카드 내용 및 제안 적용 작업 포함.
- 하이라이트된 단어/문장 변경점 표시.
- 모바일/태블릿 대응(오른쪽 최종 원고 패널 아래로 이동).

### P2 — 이후 확장: 원래 글침 아이디어와 연결

- 개인별 반복 표현 및 부사 빈도, 문장 길이 분포, 어휘 다양성 분석.
- 쉬운 단어 대체 검토(어려운 단어가 항상 나쁜 표현이라는 전제를 두지 않음).
- 사용자가 **수용한/거절한/직접 수정한** 제안 유형의 기록과 퇴고 성향 리포트.
- 과거 글과 이번 글의 습관 변화 비교.
- 로그인 및 서버 저장은 **MVP 필수 아님**. 우선 개인 브라우저에서 완결되는 흐름을 구현한다.

## 5. 권장 화면 상세와 디자인 가이드

> 기존 데모의 디자인은 참고만 한다. **기능은 유지하되 시각적 완성도는 개선**한다.

### 5.1 디자인 방향

- **키워드:** 깔끔한 에디토리얼, 조용한 서재, 절제된 생산성 도구, 넉넉한 여백.
- **피해야 할 것:** 과도한 그라데이션, 너무 많은 색상·뱃지, 게임 같은 UI, 장식적 카드 남발, 작은 본문 글자, 버튼 과밀 배치.
- **기본 색:** 미색/밝은 회백색 배경, 흰색 카드, 짙은 차콜 텍스트, 저채도 딥그린 포인트. 모드 구분은 색만 아니라 텍스트·아이콘으로 함께 표시.
- **타이포그래피:** 한국어 긴 문장을 읽기 편한 폰트(예: Pretendard 계열 또는 시스템 폰트), 본문 15~16px 이상, 여유 있는 행간.
- **정보 계층:** 페이지 제목 → 문장 카드 번호·모드 → 직접 편집창 → AI 참고 영역 → 적용 버튼.
- **반응형:** 데스크톱에서는 문장 카드 약 2/3 + 최종 원고 약 1/3. 작은 화면에서는 1열 스택.
- **인터랙션:** 모드 전환·제안 적용·복원 시 상태가 직관적으로 표시되어야 하며, 애니메이션은 짧고 절제한다.

### 5.2 시작 화면 구성

- 로고 `글침` / 작은 부제 `AI와 함께, 내 문장답게`
- 헤드라인 `글은 내가 쓰고, AI는 필요한 만큼만.`
- 본문 입력 textarea(넉넉한 크기)
- 주요 버튼 `분석하기` (명확한 primary CTA)
- 보조 버튼 `예시 글 넣기`
- 짧은 작동 안내 `① 글 입력 ② 문장별 모드 선택 ③ 직접 수정하고 완성`

### 5.3 문장 카드 기본 구성 (예시)

```text
┌──────────────────────────────────────────────────────┐
│  03  세 번째 문장                          [수정됨]   │
│  [💬 진단만]  [✨ AI 고쳐쓰기]  [🔒 고정]             │
│                                                      │
│  [여기에 문장을 직접 수정할 수 있는 입력창]           │
│                                                      │
│  ──────────────────────────────────────────────────  │
│  진단만: “강조 표현이 반복됩니다. 직접 수정해 보세요.”│
│                        [원문 복원]                    │
└──────────────────────────────────────────────────────┘

AI 고쳐쓰기 선택 시:
┌──────────────────────────────────────────────────────┐
│  AI가 제안하는 문장                                   │
│  “전시장 분위기가 좋았고 작품도 인상적이었다.”        │
│  이유: 반복된 강조어를 줄였습니다.                    │
│                [다시 제안] [이 문장에 적용]           │
└──────────────────────────────────────────────────────┘
```

### 5.4 최종 원고 패널

- 오른쪽 sticky 패널(스크롤 시 가시성 확보, 화면 높이에 맞춘 별도 스크롤도 가능).
- 제목 `완성 중인 원고`.
- 조립된 현재 원고를 읽기 쉽게 표시.
- **카드에서 직접 수정할 때마다 변경 사항을 실시간 반영**.
- `복사하기`, `TXT로 저장` 버튼.
- 빈 문장·줄바꿈·문단 보존 정책 일관되게 적용.

## 6. 상태·데이터 모델 (권장)

```ts
type EditMode = 'advice' | 'rewrite' | 'lock';

type Suggestion = {
  id: string;
  sentenceId: string;
  sourceText: string;       // 생성 당시 기준 문장
  sourceVersion: number;    // 생성 당시 버전
  suggestedText: string;    // rewrite에서만 존재해도 됨
  reason: string;
  status: 'ready' | 'stale' | 'applied' | 'error';
  isMock: boolean;
};

type SentenceCard = {
  id: string;               // 문장 삽입/수정 중에도 안정적인 ID
  paragraphId: string;
  originalText: string;     // 최초 분석 시 텍스트
  currentText: string;      // 사용자가 직접 수정 중인 텍스트
  mode: EditMode;
  version: number;
  suggestion?: Suggestion;
};

type DocumentState = {
  id: string;
  originalFullText: string; // 전체 최초 입력 원고
  cards: SentenceCard[];
  lastUpdatedAt: string;
};
```

- 문장 카드의 **현재 텍스트를 단일 진실 공급원(single source of truth)**으로 사용한다.
- AI 제안 객체는 카드의 텍스트와 분리한다. 제안 생성 자체가 원문을 변경하면 안 된다.
- 카드 모드를 변경해도 `originalText`, `currentText`가 임의로 초기화되면 안 된다.
- 버전은 문장 내용이 바뀔 때만 올리고, 모드만 바꿀 때는 필요에 따라 별도 상태로 관리한다.
- 문단/구두점/공백을 보존하기 위한 분리·재조립 로직은 테스트로 검증한다.

## 7. 기술 스택 · 개발 구조

### 권장 스택

- **Frontend:** React + TypeScript + Vite
- **Styling:** Tailwind CSS 또는 일관된 CSS Modules (컴포넌트의 재사용성 우선)
- **State:** React 상태 + 필요 시 Zustand
- **Diff:** 검증된 텍스트 diff 라이브러리 또는 간단한 자체 구현
- **Tests:** Vitest + React Testing Library; 가능하면 Playwright로 브라우저 E2E
- **Backend:** 실제 AI 연결이 필요할 때 Node.js 서버/API 또는 Python FastAPI 중 한 가지 선택
- **LLM:** 공급업체가 바뀌어도 교체 가능한 `AIProvider` 인터페이스
- **Local persistence:** 우선 localStorage/IndexedDB 중 적합한 방식 사용

### AI 연결 지침

- 프론트엔드에 비밀 API 키를 하드코딩하거나 `VITE_*` 환경 변수로 노출하지 않는다.
- 실제 모델 호출은 서버에서 수행하고, 키는 `.env` 등 서버 전용 환경 변수로 관리한다.
- 키가 없으면 **Mock AI 모드**로 서비스가 정상 동작해야 한다.
- 화면에 현재 모드(`데모 제안` / `실제 AI 사용 중`)를 명확히 표시한다.
- `advice`와 `rewrite`는 서로 다른 출력 스키마를 사용한다.
  - `advice`: `issues[]`, `explanation`, `actionableHint` (**완성된 대체 문장 금지**)
  - `rewrite`: `suggestedText`, `reason`
- `lock` 문장에 대해서는 AI 분석·수정을 요청하지 않는다. 외부 AI 전송을 위한 추가 문맥으로 사용할 경우에는 별도 명시적 설계/고지가 필요하며, 이번 MVP에서는 보내지 않는다.
- 외부 API로 원문을 보낼 때는 데이터 전송 사실을 사용자에게 알린다.
- API 호출에 실패해도 편집기 동작과 원고는 유지된다.

## 8. 반드시 테스트할 시나리오 (수용 기준)

아래 케이스를 자동 테스트 또는 직접 브라우저에서 확인하고 결과를 README에 적는다.

| ID | 동작 | 합격 조건 |
|---|---|---|
| T01 | 첫 화면에 5문장 입력 → 분석하기 | 문장별 카드 5개(예시 기준)가 생김 |
| T02 | 카드 2번 직접 타이핑 | 카드 내용과 오른쪽 최종 원고가 즉시 변경됨 |

| T04 | `AI 고쳐쓰기` 선택 → 제안 생성 | 대체 문장·수정 이유가 표시되며 원문은 그대로 |
| T05 | 2번 카드의 제안만 적용 | 2번 카드만 변경, 나머지 카드 불변 |
| T06 | 3번 카드를 `고정`으로 변경 | AI 적용 불가. 그러나 직접 타이핑은 가능 |
| T07 | 제안 생성 후 원문을 직접 수정 | 이전 제안이 stale 처리되고 바로 적용되지 않음 |
| T08 | 카드 1개 `원문 복원` | 해당 카드만 최초 분석 당시 텍스트로 복원 |
| T09 | 수정 전후 비교 | 최초 원본과 현재 원고 차이를 확인 가능 |
| T10 | 새로고침 | 임시 저장된 현재 원고·모드가 복원됨 |
| T11 | 최종본 복사/TXT 저장 | 화면에 보이는 현재 원고와 동일한 문자열이 저장됨 |
| T12 | 외부 AI 요청 실패 | 오류 메시지를 표시하고 모든 직접 편집 내용 유지 |

| T14 | 문장 사이 줄바꿈 포함 | 원고를 합쳤을 때 문단 구분이 불필요하게 사라지지 않음 |

**특히 T02, T05, T06, T07이 실패하면 제품의 핵심 가치가 무너진 것이므로 최우선 수정한다.**

## 12. Antigravity에 입력할 첫 번째 요청 (복사해 사용)

> 작업 폴더에 있는 `GLCHIM_ANTIGRAVITY_SPEC.md`를 처음부터 끝까지 읽고, 이 파일을 단일 요구사항 기준으로 삼아 **글침 웹앱을 실제로 구현해 줘.** 기획서나 정적 목업이 아니라 실행 가능한 React + TypeScript 앱을 만들어 줘. 특히 `분석하기` 후 문장별 카드 표시, `진단만 / AI 고쳐쓰기 / 고정` 모드 구분, 카드 안의 원문 직접 수정, AI 제안의 문장별 부분 적용, 고정 문장 보호, 오래된 AI 제안의 덮어쓰기 방지를 먼저 구현해. **API 키 없이도 모든 핵심 흐름이 작동하는 Mock AI 데모 모드**가 필요해. 기존 HTML의 기능 흐름은 참고하되 디자인은 더 차분하고 완성도 높은 에디터로 개선해 줘. 구현 후 앱을 실행하고 주요 테스트를 수행한 다음 README에 실행 방법과 구현 범위를 적어 줘.
